# Folio PWA: объяснение кода

Этот проект — прежний Folio с установкой, офлайн-чтением, обновлениями и мобильным меню. React отвечает за интерфейс. Service Worker отвечает за перехват запросов и сохранённые HTTP-ответы. Это два разных JavaScript-контекста: Service Worker не может напрямую менять React state или DOM.

## 1. Карта файлов

| Файл                                                     | Для чего нужен                                                              |
| -------------------------------------------------------- | --------------------------------------------------------------------------- |
| `public/manifest.json`                                   | Название, иконки, стартовый URL, область приложения и режим standalone      |
| `index.html`                                             | Подключает manifest и иконки                                                |
| `scripts/build-pwa.mjs`                                  | После Vite находит готовые файлы, вычисляет версию и создаёт `dist/sw.js`   |
| `pwa/sw.js`                                              | Исходник Service Worker: install, activate, fetch, кэширование и обновление |
| `src/pwa/register.ts`                                    | Регистрирует Worker, следит за новой версией, отправляет команду обновления |
| `src/components/PwaStatus.tsx`                           | Показывает сеть, сохранённые данные, установку и обновление                 |
| `src/services/publicData.ts`                             | Общая функция получения публичного JSON и информация об источнике ответа    |
| `src/store/refresh.ts`                                   | Обновление Redux-данных после событий PWA                                   |
| `src/pages/Offline.tsx`                                  | Офлайн-экран внутри React                                                   |
| `public/offline.html`, `offline.css`, `offline-retry.js` | Независимый резервный экран, которому не нужен React                        |
| `src/hooks/useOnline.ts`                                 | Подписка на события online/offline                                          |
| `src/components/Navbar.tsx`, `src/styles/pwa.css`        | Мобильное меню и адаптация интерфейса                                       |
| `e2e/pwa.spec.ts`                                        | Проверки в настоящем браузере                                               |

## 2. Что происходит при первом открытии

1. Браузер получает `index.html` с опубликованного сайта.
2. Загружается собранный JavaScript. `src/main.tsx` создаёт React-приложение с `QueryClientProvider` и `AuthProvider`.
3. В конце `main.tsx` вызывается `registerPwa()`.
4. В production вызывается `navigator.serviceWorker.register('/sw.js', { updateViaCache: 'none' })`.
5. Браузер запускает Worker. Срабатывает `install`.
6. Worker сохраняет оболочку приложения: HTML, ВСЕ собранные JS/CSS, включая ленивые страницы, иконки, manifest и резервную офлайн-страницу.
7. После успешной установки срабатывает `activate`. Worker очищает устаревшие собственные кэши и вызывает `clients.claim()`.
8. Страница получает событие `controllerchange`: теперь её запросы проходят через Worker. При первой установке мы повторно запрашиваем активные данные через `refreshData()`. Поэтому данные, которые успели загрузиться до установки Worker, тоже попадают в офлайн-кэш.

Первый визит требует интернета. Сообщение `App saved for offline use` означает, что оболочка сохранена. Это не означает, что пользователь скачал все публичные API-посты: данные сохраняются по мере чтения.

## 3. Manifest не сохраняет данные

В `manifest.json`:

```json
{
  "name": "Folio — Ideas worth reading",
  "short_name": "Folio",
  "start_url": "/",
  "scope": "/",
  "display": "standalone"
}
```

`name` и `short_name` — подписи приложения. `start_url` — страница запуска. `scope` — область адресов приложения. `standalone` просит браузер открывать установленное приложение в отдельном окне. Иконки 192×192 и 512×512 находятся в `public/icons`; отдельно есть maskable-иконка.

HTML подключает manifest через `<link rel="manifest" href="/manifest.json" />`. Кнопка `Install Folio` использует событие `beforeinstallprompt`, если браузер его предоставляет. В остальных случаях она показывает инструкции установки через меню браузера. Поддержка и способ установки зависят от браузера. Для опубликованного приложения нужен HTTPS; localhost подходит для разработки.

## 4. Один полный путь запроса: открываем `/posts?search=design`

### Шаг 1. React Router выбирает страницу

В `src/App.tsx` маршрут `/posts` ведёт в `PostsLayout`, затем в компонент `Posts`. Сам React Router не запрашивает данные постов: он выбирает компонент.

### Шаг 2. Компонент читает параметры адреса

В `src/pages/Posts.tsx`:

```tsx
const [params, setParams] = useSearchParams();
// ...создание filters из search/category/status/sort/page...
const { data, loading, error } = usePosts(filters);
```

Например, `filters.search` станет `design`, `filters.page` — `1`, `filters.limit` — `9`.

### Шаг 3. Хук отправляет Redux thunk

После миграции на Redux Toolkit `usePosts` использует `useAllPosts`, который отправляет `dispatch(fetchPosts())`. `extraReducers` сохраняет pending/fulfilled/rejected. Список постов хранится один раз в `posts.entities`; selector вычисляет отфильтрованную страницу из URL-параметров. Поиск проходит через debounce 300 ms.

### Шаг 4. Сервис получает исходные посты

`fetchPosts` вызывает `getAllPosts(signal)` из `blogService.ts`, затем `fetchPublicJSON('/data/posts.json', signal)`. Данные журнала — локальный публичный JSON fixture. Параметры поиска обрабатываются selector-ом через чистую `filterPosts` без новых HTTP-запросов на каждую букву.

### Шаг 5. Общая функция делает fetch

В `src/services/publicData.ts`:

```ts
response = await fetch(url, { signal, credentials: 'omit' });
```

`credentials: 'omit'` означает, что публичный запрос не отправляет cookies. Service Worker разрешает общий кэш только для таких публичных чтений по явному списку адресов. Firebase использует собственный сервис авторизации.

### Шаг 6. Service Worker перехватывает запрос

В `pwa/sw.js` обработчик `fetch` проверяет:

- метод должен быть GET;
- заголовка Authorization быть не должно;
- URL должен быть `/data/posts.json` или публичным `/posts` либо `/posts/число` JSONPlaceholder;
- credentials должны быть `omit`.

Если условия подходят, выполняется:

```js
event.respondWith(networkFirst(request, event));
```

`respondWith` говорит браузеру: «Ответ на этот запрос подготовит Worker».

### Шаг 7а. Интернет работает

`networkFirst()` делает реальный сетевой запрос с таймаутом 4 секунды. При успешном ответе:

1. `remember(DATA, request, response)` сохраняет копию в Cache Storage.
2. `event.waitUntil(...)` даёт Worker время завершить запись, даже если ответ уже передан странице.
3. `stamp(response, 'network')` добавляет заголовки `X-Folio-Source: network` и `X-Folio-Saved-At`.
4. Оригинальные данные возвращаются вызывающему `fetch`.

`response.clone()` нужен потому, что тело ответа — поток: его нельзя независимо прочитать дважды без копии.

### Шаг 7б. Интернета нет или сервер не отвечает

Worker пытается прочитать тот же URL из `folio-public-v1`. Если сохранённый ответ существует и не просрочен, он возвращается с `X-Folio-Source: cache`.

Для вызывающего кода это всё ещё обычный `Response`. Функции сервиса не обязаны отдельно читать Cache Storage.

Если копии нет, Worker возвращает 503 с `X-Folio-Offline: 1`. `fetchPublicJSON()` распознаёт этот случай и выдаёт понятную ошибку. `ErrorState` показывает `Offline` с повторной попыткой и ссылкой на сохранённые статьи.

Ошибки 401/403/404 не маскируются старым успешным ответом. Ответы с Cache-Control private/no-store не сохраняются.

### Шаг 8. Ответ преобразуется в данные

В `fetchPublicJSON()` выполняется `response.json()`. По заголовкам запоминаются источник ответа и время сохранения. `PwaStatus` подписан на эту информацию через `useSyncExternalStore` и может показать `Showing saved data`.

### Шаг 9. Сервис фильтрует результат

В `getPosts()`:

- фильтрация ищет текст в названии, тексте, имени автора, категории и тегах;
- затем применяются category и status;
- список сортируется;
- `slice()` выбирает текущую страницу;
- возвращается `{ results, count, previous, next }`.

Получается: поиск по уже сохранённому JSON работает даже без сети, потому что фильтрация локальная.

### Шаг 10. React показывает карточки

TanStack Query сохраняет результат в памяти и уведомляет компонент. `Posts.tsx` получает новые `data` и выполняет:

```tsx
data.results.map((post, i) => <PostCard key={post.id} post={post} index={i} />);
```

Полная цепочка:

```text
URL /posts?search=design
  → App / React Router
  → Posts
  → usePosts
  → TanStack Query
  → getPosts → getAllPosts
  → fetchPublicJSON
  → fetch('/data/posts.json')
  → Service Worker: fetch → networkFirst
  → сеть ИЛИ Cache Storage
  → Response → JSON
  → фильтрация, сортировка, пагинация
  → TanStack Query
  → Posts → PostCard → экран
```

## 5. Путь Community

`Community.tsx → useCommunity(uid) → getCommunityPosts(uid, signal) → fetchPublicJSON('https://jsonplaceholder.typicode.com/posts') → Service Worker → сеть/кэш`.

Для отдельного поста маршрут `/community/100` открывает `CommunityDetails.tsx`, который запрашивает `/posts/100`. Список и подробности — разные HTTP-ответы и разные записи кэша. Поэтому загрузка списка не гарантирует, что отдельный API-ответ подробностей уже сохранён.

Изменения Community — прежнее учебное поведение JSONPlaceholder: сервер подтверждает POST/PATCH/DELETE, но не сохраняет изменения постоянно. Локальные изменения показываются в памяти отдельно для каждого аккаунта и сбрасываются при перезагрузке. Страница подробностей показывает публичную API-версию, а не локальную правку. Без сети редактирование отключено; очередь отправки изменений в задание не входила.

## 6. Почему здесь два разных кэша

| Кэш            | Что хранит                                               | Переживает перезагрузку?                                         |
| -------------- | -------------------------------------------------------- | ---------------------------------------------------------------- |
| TanStack Query | Готовые JS-результаты, например отфильтрованную страницу | Нет, постоянное сохранение Query здесь не настроено              |
| Cache Storage  | HTTP-ответы: HTML, JS, CSS, JSON, изображения            | Да, пока браузер/пользователь не удалит их и пока они не истекут |

Redux thunks вызывают fetch и офлайн, позволяя Service Worker вернуть сохранённый ответ. `useRefresh` обновляет данные при восстановлении соединения. `store/refresh.ts` связывает обновление данных с PWA. Офлайн-запись завершается понятной ошибкой, очередь мутаций не реализована.

При запуске `onlineManager.setOnline(navigator.onLine)` задаёт начальное состояние сети. Это важно после перезагрузки уже без интернета: событие offline могло произойти до загрузки JavaScript. Без начальной синхронизации библиотека могла бы считать себя онлайн и пропустить возвращение соединения.

Свежесть Query (`staleTime: 60_000`) и срок хранения HTTP-ответа (7 дней) — разные вещи. Первое определяет необходимость повторного запроса в текущей вкладке, второе — возможность офлайн-чтения.

## 7. Стратегии и ограничения

- **Оболочка приложения:** предварительное сохранение; затем чтение из кэша версии активного Worker.
- **Публичные данные:** Network-first; максимум 60 записей, срок 7 дней.
- **Публичные изображения/шрифты/стили в runtime:** Cache-first; максимум 80 записей, срок 30 дней.

`cached()` проверяет срок перед выдачей. `prune()` удаляет просроченное и лишнее. Записи сериализованы через Promise-цепочку `writes`, чтобы параллельные ответы не обошли ограничение количества. Ошибка записи, например переполненное хранилище, не мешает показать успешный сетевой ответ.

В общий runtime-кэш не идут Firebase, токены, персональные страницы, запросы с Authorization и POST/PATCH/DELETE. Сохраняется только исходный публичный HTTP-ответ; правки конкретного аккаунта добавляются позже в JavaScript и в этот кэш не попадают.

## 8. Как работает обновление

1. `npm run build` запускает TypeScript, Vite, затем `build-pwa.mjs`.
2. Скрипт получает реальные имена вроде `assets/Posts-ABC123.js`, вычисляет хеш исходника Worker и файлов сборки, записывает версию в `dist/sw.js`.
3. После публикации браузер обнаруживает изменённый `sw.js`.
4. Новый Worker в событии install создаёт собственный `folio-shell-НОВАЯ_ВЕРСИЯ` и скачивает все его файлы.
5. Он ждёт в состоянии waiting. Старое приложение продолжает работать со своей оболочкой.
6. `register.ts` сообщает интерфейсу, что обновление доступно. Появляется кнопка `Update now`.
7. Кнопка вызывает `applyUpdate()`, который посылает `{ type: 'SKIP_WAITING' }` ожидающему Worker.
8. Worker выполняет `skipWaiting()`. На activate удаляются старые собственные кэши, затем `clients.claim()` переключает вкладки.
9. Обработчик `controllerchange` перезагружает старые вкладки. Загружается согласованный комплект новых HTML/JS/CSS.

Публичный `folio-public-v1` сохраняется при обновлении интерфейса. Чужие кэши не удаляются. Ручная очистка Browser Storage не нужна. Перед обновлением интерфейс просит закончить несохранённые правки, потому что вкладки перезагрузятся.

## 9. Офлайн-страница и мобильная версия

`navigator.onLine` используется для индикатора, но это не доказательство доступности сервера. Кнопка Retry connection делает настоящий запрос к `/manifest.json?connection-check=...` с таймаутом и `cache: 'no-store'`. Этот URL с параметром специально не совпадает с предкэшированным manifest.

Известные маршруты получают сохранённый React HTML, а их данные загружаются независимо. Для неизвестного адреса, который не удаётся открыть без сети, Worker возвращает автономный `offline.html`. При переходе внутри React на неизвестный адрес без сети тоже показывается офлайн-экран.

Меню в `Navbar.tsx` раскрывается кнопкой с `aria-expanded` и `aria-controls`, закрывается при переходе и по Escape. CSS перестраивает карточки, фильтры, dashboard, формы и подробности для узких экранов. Интерактивные элементы имеют минимальную высоту 44 px. Предпочтение reduced-motion отключает анимации.

## 10. Как запустить и проверить самостоятельно

```bash
npm ci
npm run build
npm run preview
```

Открой адрес preview. PWA включается в production-сборке, а не в `npm run dev`: это защищает разработку от устаревшего кэша исходников.

Автоматические проверки:

```bash
npm run lint
npm test
npm run build
npm run test:e2e
```

Для браузерных тестов нужен Chromium (`npx playwright install chromium`). В Windows с установленным Edge можно выполнить в PowerShell `$env:PLAYWRIGHT_CHANNEL='msedge'`, затем `npm run test:e2e`.

Браузерные тесты используют контролируемые ответы внешнего API для воспроизводимости, но настоящий Service Worker, Cache Storage, загрузку сборки и переключение сети. Тест обновления временно изменяет только `dist/sw.js` и восстанавливает его в finally. Запускай тесты на локальном preview, не на production.

Ручной сценарий: открой Explore и Community, прочитай отдельный публичный пост, дождись сохранения приложения. Затем отключи сеть в DevTools, перезагрузи страницу. Прочитанный пост должен открыться с отметкой сохранённых данных. Ещё не скачанный API-пост должен показать офлайн-экран. Верни сеть — активные данные обновятся.

Проверки реальной авторизации требуют твоего Firebase-проекта; автоматические auth-тесты используют mock Firebase и не выполняют вход в реальный аккаунт.
